# WebView2/Tauri 2 Constraints — Findings Brief

Scope: read-only research for Tauri 2 Windows/WebView2 app w/ `withGlobalTauri: true`, no `@tauri-apps/api` npm dep, capability file per task context.

## 1. `window.__TAURI__.app.getVersion()` — will it work as-is?

**Yes, should work unchanged.** `app` module is exposed on global `window.__TAURI__` when `app.withGlobalTauri: true` (confirmed: [Tauri v2 config migration docs](https://v2.tauri.app/start/migrate/from-tauri-1/), [tauri-apps/tauri discussion #11511](https://github.com/orgs/tauri-apps/discussions/11511)).

Permission chain confirmed via 2 independent lookups of the same authoritative page:
- `core:default` permission set transitively includes `core:app:default` (and 8 other default sets: event, image, menu, path, resources, tray, webview, window). Source: [Core Permissions | Tauri](https://v2.tauri.app/reference/acl/core-permissions/) (fetched twice, consistent).
- `core:app:default` includes `allow-version`, `allow-name`, `allow-tauri-version`, `allow-identifier`, `allow-bundle-type`, `allow-register-listener`, `allow-remove-listener`, `allow-supports-multiple-windows`.

Repo's `default.json` has `"core:default"` in its permissions array (confirmed by reading `src-tauri/capabilities/default.json` directly) → `getVersion()` is authorized without any capability-file change.

**Residual doubt (small, not zero):** couldn't fetch the dedicated `core:app` permission-set page directly (404 on `/reference/acl/app/` — wrong URL, correct path is likely `/reference/acl/core-app/` or similar; did not re-resolve). Confidence rests on the core-permissions summary page rather than the app-specific page. There's also a documented Windows-specific timing bug where `window.__TAURI__` is `undefined` during top-level script execution ([tauri-apps/tauri#12990](https://github.com/tauri-apps/tauri/issues/12990)) — irrelevant if called after DOMContentLoaded/on a user action, but relevant if the app calls `getVersion()` at module top-level/inline `<script>` before Tauri injects the global.

**Robustness comparison — which approach for this exact config:**
- `window.__TAURI__.app.getVersion()`: fewer moving parts (no new Rust command), but depends on (a) permission ACL staying correct across Tauri upgrades, (b) global-injection timing, (c) implicit trust that `core:default` won't be pared down. It is also less discoverable if it silently starts failing (rejected promise, no compile-time signal).
- Rust `#[tauri::command]` returning `env!("CARGO_PKG_VERSION")` invoked via `window.__TAURI__.core.invoke`: 100% robust against ACL churn (no permission needed for a locally-registered command beyond it being callable — actually custom commands still need a capability entry for their identifier, e.g. `"identifier": "allow-get-app-version"` style, but that's explicit and version-controlled by the app, not an upstream default that can move), avoids injected-global timing entirely once the command is invoked from JS after app init, and version string is resolved at Rust compile time (guaranteed correct build-time value, no IPC round-trip surprises).

**Recommendation:** `window.__TAURI__.app.getVersion()` is fine to keep given current capability file, but the Rust-command fallback is marginally more robust long-term because it removes dependency on Tauri's internal default-permission composition (which is framework-owned and could change across major versions) — trade-off is +1 tiny Rust command + capability entry. Given repo already hand-lists granular `core:window:allow-*` permissions instead of relying on `core:window:default`, the project's own convention leans toward explicit permissions — the Rust-command approach is more consistent with that existing pattern. Low-severity decision either way; not worth churn unless `getVersion()` is observed failing.

## 2. WebView2 CSS support

### CSS custom properties `var()` / fallback
Standard, widely supported since Chrome 49 (WebView2 evergreen is far newer than that floor). `var(--x, fallback)` fallback can itself contain commas (`var(--x, red, blue)` → fallback is `red, blue`) — a real gotcha if a fallback value is itself a comma-separated list (e.g. font-family fallback stacks) — wrap or restructure. Source: [MDN Using CSS custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties). No WebView2-specific gotchas found beyond general Chromium behavior — could not verify any WebView2-only divergence.

### `:focus-visible`
Supported, Baseline "widely available" since ~March 2022, landed in Chrome/Chromium **86**. Source: [MDN :focus-visible](https://developer.mozilla.org/en-US/docs/Web/CSS/:focus-visible). Evergreen WebView2 tracks current Edge/Chromium stable, far above 86, so no version risk.

**On the specific "mouse click on `<button>` incorrectly matches `:focus-visible`" claim: not confirmed for `<button>`.** Per spec and MDN's own example, clicking a `<button>` with a mouse does NOT trigger `:focus-visible` in Chromium — that's the intended, correct behavior (focus ring shown only for keyboard/programmatic focus). The known Chromium quirk is scoped to `<select>` elements specifically (a mouse click on `<select>` is treated by Chromium as non-mouse input, so it incorrectly matches `:focus-visible`) — see [w3c/csswg-drafts#5822](https://github.com/w3c/csswg-drafts/issues/5822). If this app has `<select>` elements relying on `:focus-visible` styling, that's the one real caveat; plain `<button>` is unaffected. Recommend not assuming a button-specific bug exists — could not find evidence of one.

### `::-webkit-scrollbar`
Still works in current Chromium/WebView2 — legacy, never standardized, but not deprecated/removed. Confirmed: [Chrome for Developers scrollbar styling](https://developer.chrome.com/docs/css-ui/scrollbar-styling), [MDN ::-webkit-scrollbar](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/::-webkit-scrollbar). **Deprecation-risk note:** the standardized `scrollbar-width`/`scrollbar-color` (Chrome 121+) now take precedence over `::-webkit-scrollbar-*` when both are present and the standard properties are set to non-`auto` values — i.e. mixing both approaches on the same element causes the standard one to silently win. Not itself deprecated, but Chromium's own direction favors the standard properties; safe to keep `::-webkit-scrollbar` for now if not also setting `scrollbar-width`/`scrollbar-color` on the same element, but plan eventual migration since it's the long-term standard.

### `:has()`
Supported since Chrome/Chromium **105** (Aug 2022). Source: [Chrome for Developers: :has() the family selector](https://developer.chrome.com/blog/has-m105/), [caniuse.com/css-has](https://caniuse.com/css-has). Safe to use given evergreen WebView2. Caveats: can't nest `:has()` inside `:has()` (chaining is fine), no pseudo-elements inside `:has()`, `:visited` always evaluates false inside it, and there are known perf costs for complex/broad selectors — keep `:has()` selectors narrow/scoped.

### `backdrop-filter` breaking `position: sticky`/`fixed` descendants
**Confirmed mechanism, this is spec-correct behavior, not a bug.** A non-`none` `backdrop-filter` (like `filter` and `transform`) on an ancestor creates a new **containing block** for that ancestor's `fixed`- and `absolute`-positioned descendants (and establishes a stacking context). Once that happens, `top/right/bottom/left/inset` on the fixed-position descendant resolve against the filtered ancestor's padding box instead of the viewport — the element is still visually "fixed" relative to that ancestor, effectively trapping it inside that box rather than the viewport. `position: sticky` descendants are also affected similarly (sticky's scroll-container/containing-block chain changes). Sources: [konadu.dev — backdrop-filter Breaks position:fixed](https://konadu.dev/backdrop-filter-breaks-position-fixed), [Mozilla Bugzilla 1909463 — backdrop-filter doesn't work with position:sticky in complex pages](https://bugzilla.mozilla.org/show_bug.cgi?id=1909463) (cross-engine, same root cause), CSS spec discussion at [w3.org fxtf-drafts mail archive](https://lists.w3.org/Archives/Public/public-fxtf-archive/2022Jul/0001.html). **Practical implication for this app:** don't put `backdrop-filter` on an ancestor of anything that needs `position: sticky`/`fixed` to escape to the viewport/window — either apply `backdrop-filter` to a leaf/sibling element instead of a wrapping ancestor, or restructure so the sticky/fixed element is not a descendant of the filtered element.

## 3. Tauri 2 drag region

Confirmed via official docs: `data-tauri-drag-region` "will only work on the element to which it is directly applied" — not inherited by descendants; child interactive elements (buttons, inputs) need their own `data-tauri-drag-region="false"`-equivalent handling or simply omit the attribute so they remain clickable. Source: [Tauri Window Customization docs](https://v2.tauri.app/learn/window-customization/), corroborated by [tauri-apps/tauri commit 4f1e87f — "change drag element detection to data attr"](https://github.com/tauri-apps/tauri/commit/4f1e87f87bbd4e094116b83edff448847da178ea) and multiple GH issues confirming per-element (not inherited) behavior, e.g. [#9901](https://github.com/tauri-apps/tauri/issues/9901).

**`-webkit-app-region` / `app-region` in Tauri 2 — more nuanced than pure "no effect," but net conclusion is the same:**
- `-webkit-app-region`/unprefixed `app-region` IS a real Blink/Chromium CSS feature (not Electron-invented) — but Chromium only applies it when the **embedding host** enables non-client-region support. In WebView2 this requires the host app to explicitly set `ICoreWebView2Settings9.IsNonClientRegionSupportEnabled = true` before navigation. Source: [MicrosoftEdge/WebView2Feedback #200 — Implement draggable regions](https://github.com/MicrosoftEdge/WebView2Feedback/issues/200), [ICoreWebView2Settings9 docs](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2settings9?view=webview2-1.0.2792.45).
- Electron enables this at the Chromium/CEF level as part of its frameless-window implementation, which is why the CSS property "just works" there.
- **Tauri 2 does not expose or set `IsNonClientRegionSupportEnabled`** — its own drag mechanism (`data-tauri-drag-region` → JS listens for mousedown → calls Rust `start_dragging` via IPC) is entirely separate from the browser CSS property. No Tauri API surface for this was found — could not verify a definitive negative (absence is hard to prove from docs), but no evidence exists that Tauri sets this WebView2 setting, and the official docs make zero mention of `-webkit-app-region`/`app-region` ([Window Customization | Tauri](https://v2.tauri.app/learn/window-customization/) — fetched, confirmed no mention).
- **Net effect for this repo:** `-webkit-app-region`/`app-region` CSS will have no effect in this app's WebView2 instance since the required host setting isn't enabled by Tauri. Practical conclusion matches the task's framing (Electron-only mechanism, no effect here) even though the underlying browser-engine story is more nuanced than "Electron invented it."

## 4. `minWidth`/`minHeight` units — logical or physical pixels

**Logical (CSS) pixels, confirmed via 2 independent sources:**
- [docs.rs `tauri_utils::config::WindowConfig`](https://docs.rs/tauri-utils/latest/tauri_utils/config/struct.WindowConfig.html) — field docs literally state: "The window width in logical pixels" / "The min window width in logical pixels" (same wording for height/min_height).
- Corroborated by community discussion referencing the same struct: [tauri-apps/tauri discussion #7525](https://github.com/tauri-apps/tauri/discussions/7525).

Repo's `tauri.conf.json` has `minWidth: 400, minHeight: 200` (confirmed by reading the file). **Yes**: on a 150%-DPI display, `minWidth: 400` still means the OS won't let the window shrink below 400 CSS/logical px of webview viewport width — Windows/WebView2 handles the logical→physical scaling so the toolbar's CSS layout math (built in logical px) stays correct regardless of DPI. Toolbar-clipping risk at the min-width boundary is a pure CSS layout question (does the toolbar's content fit in 400px), not a DPI-scaling question.

## 5. Flexbox `min-height: 0` for `overflow-y: auto` in a flex column

**Standard, spec-correct behavior, not a Chromium-only quirk** — though Chromium has historically been the most "forgiving"/inconsistent among engines about auto-defaulting this in some cases. Per CSS Flexbox spec, the initial value of `min-height`/`min-width` on a flex item is `auto`, which (for non-`visible` overflow) resolves to the *smaller of* the content's min-content size or the item's specified size — this is what causes a flex child with text/scrollable content to refuse to shrink below its content height, silently breaking `overflow-y: auto` on a nested scroll container. Explicitly setting `min-height: 0` (or `min-height: auto` won't help; must be `0` or a definite value) overrides that auto min-sizing floor and lets the item shrink to fit the flex container, allowing the inner `overflow-y: auto` to actually activate. This is documented as "Flexbug #1" and is universal across engines (Chromium, Firefox, WebKit) per spec — Chromium is not an outlier here; do not expect WebView2 to differ from desktop Chrome. Sources: [philipwalton/flexbugs #241](https://github.com/philipwalton/flexbugs/issues/241), [CSS WG mailing list on min-width/height:auto for flex items](https://lists.w3.org/Archives/Public/www-style/2014Jul/0317.html), cross-engine confirmation via [Mozilla Bugzilla 1114904](https://bugzilla.mozilla.org/show_bug.cgi?id=1114904) (Firefox tracking the same spec behavior). Fix pattern for this repo: any flex-column ancestor of a scrollable region needs `min-height: 0` on every flex item in the chain down to the scrolling element, not just the immediate scroll container.
